## Rationale
Through the feasibility lens the question is not which plan cites the packet most fluently (all four cite it accurately — int8-below-small, encoder-never-fp16, VAD-for-hallucinations, word-timestamps-demoted-to-sentence-contract appear in every ml_plan), but which plan's ML will actually run, at the claimed speed, on the hardware named in its own potato story. Espalier-Flutter wins that test. The canonical user is a language learner on a cheap Android phone, and the fleet's distribution norm is a sideloaded APK; on that phone, native whisper.cpp with NEON threads inside a foreground service is the only proposal where a 40-minute multilingual transcription plausibly completes at 'roughly realtime' with screen off — the three browser proposals are honest that the same job is a screen-on, wake-locked, COOP/COEP-hack-dependent multi-hour vigil. Its reliability engineering is also the strongest on the panel by the 'designed, not asserted' standard: it imports the actually-tested domovoi ResumableTransfer (verified present at DomovoiDiscernment/lib/src/transfer) rather than porting its laws, and it specifies the best reliability artifact proposed by anyone — a kill-point sweep property test asserting the resumed transcript is byte-identical to the uninterrupted run, committed one-Drift-transaction-per-window. Its deductions are real but honestly declared: no dedicated MT runtime at v1 (opus-mt/NLLB deferred behind a hand-rolled ONNX seq2seq loop it correctly names its riskiest item — interim translation leans on LLM quality plus Whisper's native translate task), zero browser-local ML at launch (a literal miss on the brief's 'T1 = WASM tiny models' rung for anyone who can't sideload), and the weakest iOS story (T0 web only). Verdict is therefore explicitly hybrid: build Espalier-Flutter's native spine, but steal (a) Arbor's .ohparcel 'cuttings' / Grist's course-carried layers — a file format where transcript + sentence alignment + translations travel INSIDE the shared artifact, which is the single best potato-floor mechanism on the panel and is absent from the Flutter proposal's course format; (b) the TS proposal's distill-time discourse (Socratic follow-ups baked into the .ohcourse so a zero-ML phone gets construction-and-discourse study with no runtime inference); and (c) pull the Phase-6 web ML tier forward at least to whisper-tiny-in-browser, since the packet shows transformers.js v4 makes that a bounded, cited task. Arbor ranks second: identical well-cited client stack, the best word-timing story anywhere (hearth whisper.cpp DTW timestamps), the deepest secure-context awareness (localhost-console-is-secure-context, @noble crypto for insecure contexts, WebTransport-with-cert-hashes correctly triaged as a spike with the APK Dart bridge as the guaranteed path) — held back only by scope, the rosiest potato timing claim ('lunch break, 0.5–2× realtime' WASM on a 1–2GB phone; Grist's 'overnight job' is the honest number), and a hearth-shaped value center the potato-only household never sees. The TS Espalier is third: the most complete single-substrate tier table with a named runtime for every capability at every tier, excellent checkpoint/download design — but it keeps ML on the substrate whose jank motivated the rebuild, its T1 speed is hostage to the coi-serviceworker hack it lists as a risk, and its Android surface (a WebView shell that replaces the Trellis install base in place) never once discusses WebView ML reality: WebGPU availability in Android WebView, no foreground service, background process death. Grist & Trellis is fourth on this lens despite the most honest speed claims and the most explicit iOS section, because its flagship T3 mechanism fails the lens's core test: 'Stove Studio serves the Grist bundle same-origin over LAN' is asserted to dissolve the CORS/mixed-content wall (the no-CORS premise I verified in stove_server.dart), but a page served from http://LAN-IP is not a secure context — no service worker, no OPFS, no WebGPU, no crypto.subtle — so the served Grist as written cannot run its own storage, ML, or OHBK crypto layers. Arbor's transport matrix is the existence proof that this problem was findable and solvable; Grist didn't look.

## Red flags
- Grist & Trellis — Stove Studio secure-context hole (near-fatal to its T3 story): serving the Grist bundle over http:// from the LAN stove yields an insecure context, which disables service workers, OPFS, WebGPU, and crypto.subtle — the exact APIs Grist's storage, ML tiers, and OHBK layer are built on. The claimed 'same-origin kills both blockers' mechanism does not run as written; it needs Arbor's treatment (localhost console, WebTransport cert hashes, or a native bridge).
- Espalier (TS PWA) — the Android surface is a WebView shell that in-place-replaces the Flutter Trellis install base (versionCode 4), yet the proposal never addresses WebView ML reality: WebGPU in Android WebView is not dependably available, there is no foreground service, and a backgrounded WebView app can be frozen or killed — so the potato's primary surface may be strictly worse at ML than plain Chrome. (It does honestly flag the SharedPreferences data cliff of the in-place upgrade.)
- Espalier (Flutter) — v1.0 ships zero in-browser ML, deferring the brief's explicit 'T1 = WASM tiny models' rung to Phase 6; any user who cannot sideload (managed devices, all of iOS) gets no local inference at all. Honestly declared, but it is a hard-requirement gap, not a nuance.
- Espalier (Flutter) — no dedicated translation runtime at launch: opus-mt/NLLB wait on a hand-rolled onnxruntime seq2seq decode loop (KV cache + SentencePiece) the proposal itself calls its riskiest ML item; until then the flagship language learner's text translation rides local-LLM quality (0.5–1.5B) or household/BYOK tiers.
- Arbor — the browser↔hearth WebTransport path requires serverCertificateHashes over a maintained Node HTTP/3 server implementation, which is near research-grade in the Node ecosystem, and Safari support is unproven; correctly hedged with the APK bridge and localhost console, but nothing user-facing may be marketed on the PWA-to-hearth channel until the spike lands.
- Arbor — potato timing overclaim: 'a 40-minute Spanish podcast transcribes in roughly a lunch break at 0.5–2× realtime' on a 1–2GB WASM phone; the 2× end is fantasy on that hardware and even 0.5× assumes the COOP/COEP thread hack holds. Grist's 'overnight job' phrasing is the honest calibration for the identical stack.
- All three browser-ML proposals — transformers.js v4 is months old with a rewritten C++ WebGPU runtime (the fp16 encoder bug is the known precedent), and WASM-thread performance on GitHub Pages depends on the coi-serviceworker COOP/COEP injection hack, which any browser tightening could break; T1 potato transcription speed is hostage to both.
- Espalier (Flutter) — the potato's browser-only T0 experience is the heaviest on the panel: Flutter web + CanvasKit + drift-wasm boot on a $90 phone is the reason the fleet playbook has a slow-boot-spinner entry; the T0 rung the brief guarantees is served worse in-browser than by any of the vanilla/Preact shells.
- Panel-wide — multilingual word-level timestamp sync remains fragile everywhere (_timestamped ONNX exports #1357/#1590/#1198; non-English drift): every proposal correctly demotes to a sentence-level contract, so any future marketing of multilingual word-karaoke would be an overclaim; the only robust word-timing path proposed is Arbor's hearth-side whisper.cpp DTW.
