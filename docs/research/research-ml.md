# 2026 Browser / On-Device ML Landscape — Research Report

## 1. transformers.js v3.x (and the v4 surprise)

**Version reality check:** v3 (Oct 2024) introduced WebGPU support ("up to 100x faster than WASM"), the full dtype menu (fp32, fp16, q8/int8/uint8, q4, bnb4, q4f16) with per-module dtype for encoder-decoder models, and the move to `@huggingface/transformers` ([v3 blog](https://huggingface.co/blog/transformersjs-v3)). **Transformers.js v4 shipped Feb 9, 2026** with a completely rewritten C++ WebGPU runtime co-developed with the ONNX Runtime team, tested across ~200 architectures, and WebGPU now also works in Node/Bun/Deno ([v4 blog](https://huggingface.co/blog/transformersjs-v4), [releases](https://github.com/huggingface/transformers.js/releases)). Any new project should target v4, not v3.

**Multilingual Whisper models + quantized sizes** (all on onnx-community, multilingual, encoder + decoder-with-past pairs; sizes from HF file trees):

| Model | Practical quantized total | Detail |
|---|---|---|
| whisper-tiny | **~41 MB** (int8) | enc int8 10.1 MB + dec int8 30.5 MB ([tree](https://huggingface.co/onnx-community/whisper-tiny/tree/main/onnx)) |
| whisper-base | **~77 MB** (int8) | enc int8 23.2 MB + merged dec int8 53.7 MB ([tree](https://huggingface.co/onnx-community/whisper-base/tree/main/onnx)) |
| whisper-small | **~248 MB** (int8) | enc int8 92.3 MB + dec int8 156 MB ([tree](https://huggingface.co/onnx-community/whisper-small/tree/main/onnx)) |
| whisper-large-v3-turbo | **~563 MB** (q4f16) | enc q4f16 370 MB + dec q4f16 193 MB; enc int8 645 MB, fp32 enc 2.55 GB ([tree](https://huggingface.co/onnx-community/whisper-large-v3-turbo/tree/main/onnx), [model](https://huggingface.co/onnx-community/whisper-large-v3-turbo)) |

Note the q4 decoder anomaly on small models: tiny's q4 decoder (86.6 MB) is *larger* than its int8 (30.5 MB) — int8/q8 is the right pick below small.

**Pipeline options:** the ASR pipeline accepts `language` (ISO hint), `task: 'transcribe' | 'translate'` (translate = X→English only, inherited from Whisper), `return_timestamps: true | 'word'`, and `chunk_length_s` / `stride_length_s` (canonical long-audio recipe: 30 / 5 overlapping windows) ([AssemblyAI walkthrough](https://www.assemblyai.com/blog/offline-speech-recognition-whisper-browser-node-js), [pipeline docs](https://huggingface.co/docs/transformers.js/api/pipelines)).

**Word-level timestamps — real but rough:** word-level requires special `_timestamped` ONNX exports that keep cross-attentions (e.g. [whisper-large-v3-turbo_timestamped](https://huggingface.co/onnx-community/whisper-large-v3-turbo_timestamped); announced as "Whisper Timestamped: multilingual + word-level" by [Xenova](https://huggingface.co/posts/Xenova/386072637398041)). Open wounds: WebGPU pipeline + word-level was a long-running gap ([#820](https://github.com/huggingface/transformers.js/issues/820)); turbo_timestamped shipped with broken timestamps (Jul 2025, [#1357](https://github.com/huggingface/transformers.js/issues/1357)); accuracy complaints ([#805](https://github.com/huggingface/transformers.js/issues/805)); WebGPU fp16 encoder precision degrades output (Mar 2026, [#1590](https://github.com/huggingface/transformers.js/issues/1590)) — run the encoder fp32/int8 on WebGPU. **Streaming:** no true streaming word timestamps; chunk callbacks (`on_chunk_start/end`) only fire with `return_timestamps: true`, not `'word'` ([#1198](https://github.com/huggingface/transformers.js/issues/1198)). Long audio is chunked, not streamed.

## 2. whisper.cpp → WASM

Mature but CPU-bound: the official whisper.wasm example does **~2-3x realtime for tiny/base on a modern CPU**, supports models only up to `small`, caps the demo at 120 s audio, greedy sampling only, and has no GPU path in the browser ([whisper.wasm README](https://github.com/ggml-org/whisper.cpp/blob/master/examples/whisper.wasm/README.md)). transformers.js + WebGPU beats it substantially (a 76 MB model at 5-8x realtime claimed by [whisperstt](https://whisperstt.com/blog/transcribe-audio-in-browser/); comparison overview at [OfflineTTS](https://offlinetts.com/blog/browser-speech-recognition-whisper-comparison/)). whisper.cpp has native token-level timestamps, but in-browser the ecosystem has consolidated on transformers.js (e.g. [browser-whisper](https://github.com/tanpreetjolly/browser-whisper) wraps transformers.js with WASM fallback). Verdict: whisper.cpp WASM is the fallback for non-WebGPU browsers, not the primary path.

## 3. In-browser text LLMs

- **WebLLM** (`@mlc-ai/web-llm`): WebGPU-required, Apache-2.0, 18.5k stars; fastest in-browser inference (Phi-3.5-mini at 71 tok/s per its [paper](https://arxiv.org/html/2412.15803v2)); prebuilt MLC weights include Qwen3-0.6B/1.7B/4B ([mlc-ai/Qwen3-0.6B](https://huggingface.co/mlc-ai/Qwen3-0.6B-q4f16_1-MLC)); lags newest architectures (Qwen3.5 Gated-DeltaNet unsupported, open request [#778](https://github.com/mlc-ai/web-llm/issues/778)); loads whole model through JS memory ([repo](https://github.com/mlc-ai/web-llm)).
- **wllama**: llama.cpp WASM binding, **V3 added WebGPU + multimodal**; auto single/multi-thread; 2 GB ArrayBuffer limit worked around by `llama-gguf-split` 512 MB chunks; streams model from OPFS into buffers (more memory-efficient than WebLLM); MIT, active ([repo](https://github.com/ngxson/wllama), [comparison](https://localmode.dev/blog/three-llm-providers-one-api)).
- **Smallest useful models:** Qwen2.5-0.5B-Instruct — **Apache-2.0, ungated**, 0.49B params, 32k context, ~500 MB q8, "runs in 1-2 GB browser memory, handles basic classification" ([HF](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct), [maddevs](https://maddevs.io/writeups/running-ai-models-locally-in-the-browser/)). Llama-3.2-1B: gated behind the Llama community license on HF. **Gemma-2-2b-it: gated** — accept-Google's-terms wall, "gemma" license, actually ~3B params ([HF](https://huggingface.co/google/gemma-2-2b-it)). For a FLOSS no-account product, Qwen (2.5/3) is the only friction-free family.

## 4. Translation done small

- **opus-mt per-pair** (Xenova conversions, e.g. [opus-mt-en-es](https://huggingface.co/Xenova/opus-mt-en-es/tree/main/onnx)): en-es quantized runs ~52 MB (int8 encoder) + ~60 MB decoder ≈ **~110 MB per direction per pair**; many pairs are smaller (the folk "40-80 MB" number matches the older v2 `quantized` single-file totals for smaller pairs). Fast, decent for high-resource pairs, but one model per direction.
- **NLLB-200-distilled-600M** ([Xenova conversion](https://huggingface.co/Xenova/nllb-200-distilled-600M)): 200 languages, one model, but **>800 MB download and 2-5 s per complex sentence** at 8-bit in browser ([alexop.dev build report](https://alexop.dev/posts/building-client-side-ai-translator-vue/)); WebGPU use has open issues ([#1286](https://github.com/huggingface/transformers.js/issues/1286)), plus a pruning bug history ([#843](https://github.com/huggingface/transformers.js/issues/843)). Coverage vs weight: NLLB wins coverage, opus-mt wins size/speed.
- **Newer + small:** Chrome's built-in **Translator API** — stable since Chrome 138, on-device models downloaded by the browser (not your quota), Edge 148 too, but **desktop-only, not on mobile** and Chromium-only ([Chrome docs](https://developer.chrome.com/docs/ai/translator-api)). Good progressive enhancement, not a foundation.

## 5. Browser TTS

- **kokoro-js** (powered by transformers.js): Kokoro-82M v1.0 ONNX — fp32 326 MB / fp16 163 MB / **q8 92.4 MB** / q4f16 154 MB, `dtype` selectable, Apache-2.0; the **ONNX/browser package exposes 28 voices, American + British English only** — the 9-language claim belongs to the Python model with espeak G2P, not the JS path ([Kokoro-82M-v1.0-ONNX](https://huggingface.co/onnx-community/Kokoro-82M-v1.0-ONNX), [Xenova announcement](https://huggingface.co/posts/Xenova/503648859052804), [hexgrad/kokoro](https://github.com/hexgrad/kokoro)). Quality: best-in-class for the size; near-commercial for short EN clips ([review](https://www.visionstory.ai/open-source/kokoro-tts)).
- **Piper WASM**: whole pipeline (phonemizer + ONNX) compiled to WASM, ~60 MB voices, CPU-only (no WebGPU needed), 3-5x realtime, 22.05 kHz, MIT; multiple maintained forks ([piper-tts-web](https://github.com/Mintplex-Labs/piper-tts-web), [Poket-Jony fork](https://github.com/Poket-Jony/piper-tts-web), [overview](https://offlinetts.com/tts/piper/)). This is the multilingual browser-TTS answer (Piper's voice catalog spans dozens of languages), at lower naturalness than Kokoro.
- **SpeechT5** in transformers.js ([Xenova/speecht5_tts](https://huggingface.co/Xenova/speecht5_tts)) works but is English-only and audibly a generation behind both — legacy option.

## 6. Storage + PWA platform reality (2026)

- **Quotas** ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)): Chrome/Edge — up to **60% of disk per origin** (best-effort *and* persistent). Firefox — 10% of disk capped at 10 GiB best-effort; 50% of disk if persistent. Safari — **~60% of disk for Safari and Home-Screen web apps** (~15% inside in-app WebViews). **OPFS counts against the same quota** and follows the same eviction. Eviction is whole-origin, LRU.
- **Safari 7-day eviction**: script-writable storage (IndexedDB, localStorage, SW registrations, Cache) deleted after 7 days of no interaction — **but Home-Screen-installed web apps are exempt in practice: they keep their own usage counter separate from Safari** ([Apple dev forums](https://developer.apple.com/forums/thread/710157), [MagicBell 2026 guide](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)). Installing is the mitigation; iOS can still purge a PWA's storage after weeks of disuse.
- **`navigator.storage.persist()`**: Chrome/Safari auto-grant based on engagement heuristics, Firefox prompts; on Chrome it upgrades to only-user-can-clear ([MDN persist()](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)). On iOS its protection against the 7-day timer is under-documented; developers report it helps, don't bet on it.
- **iOS install post-DMA**: Apple announced removal of EU Home-Screen web apps in iOS 17.4 beta ([Register](https://www.theregister.com/2024/02/16/apple_web_apps/)), then reversed and kept them, WebKit-based ([Apple DMA support page](https://developer.apple.com/support/dma-and-apps-in-the-eu/)). Third-party engines via BrowserEngineKit exist on paper; **zero browsers have shipped one as of early 2026** ([MobiLoud 2026 guide](https://www.mobiloud.com/blog/progressive-web-apps-ios)).
- **Safari WebGPU: shipped and default-on in Safari 26 / iOS 26** (Sept 2025); all major browsers now ship WebGPU by default ([implementation status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status), [webgpu.com](https://www.webgpu.com/news/webgpu-hits-critical-mass-all-major-browsers/)). Caveat: only on up-to-date iOS.
- **Long jobs (40-min transcription)**: background-tab *timers* get clamped (500 ms/2 s/5 s tiers), but **Web Worker threads are not throttled in background tabs** — compute continues ([supercharge](https://www.superchargebrowser.com/features/js-throttling/), [getintechs](https://www.getintechs.com/blog/inactive-tab-throttling), [Medium](https://medium.com/@adithyaviswam/overcoming-browser-throttling-of-setinterval-executions-45387853a826)). Android Chrome may still freeze/discard whole tabs under memory pressure; iOS Safari suspends the entire page (workers included) when backgrounded — there is no true background processing on iOS PWAs ([MagicBell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)). Practical design: run inference in a worker + hold a **Screen Wake Lock** in the foreground. Wake Lock is now universal (Safari 16.4+, >94% global support; [caniuse](https://caniuse.com/wake-lock), [web.dev](https://web.dev/blog/screen-wake-lock-supported-in-all-browsers)); the installed-iOS-PWA wake-lock bug was fixed in iOS 18.4 ([Progressier](https://progressier.com/pwa-capabilities/screen-wake-lock)).

## 7. FSRS vs SM-2

FSRS-6 with per-user optimization reaches mean log loss 0.344 and **beats SM-2 in 99.6% of benchmark collections**; simulations on 500M+ real Anki reviews show ~20-30% fewer reviews for equal retention ([Neurako digest of srs-benchmark](https://www.neurako.com/blog/fsrs-vs-sm2-spaced-repetition-algorithms-compared), [flica](https://flica.app/article/fsrs-vs-sm2)). Honest caveats from the same sources: the 20-30% figure is simulation, not an RCT, and SM-2 had to be retrofitted with probability formulas to be comparable. **ts-fsrs** ([repo](https://github.com/open-spaced-repetition/ts-fsrs)): implements FSRS-6, MIT, ~740 stars, Node ≥20, actively released; **scheduling works out of the box with default parameters fit on hundreds of millions of reviews — per-user parameter fitting is a separate package** (`@open-spaced-repetition/binding` optimizer), so a Trellis-style app can ship FSRS with defaults and add fitting later.

## 8. Podcast/RSS from a serverless PWA — the CORS reality

Arbitrary feeds and enclosures mostly don't send `Access-Control-Allow-Origin`, so `fetch()` from a PWA fails; `<audio src>` *can play* cross-origin but the page can't read bytes (no offline caching, no transcription input). What serverless players actually do: require a reverse proxy ([pager](https://github.com/flysteur-dev/pager) — "requires at least a reverse proxy to get around CORS"), pre-fetch via CI ([rssTea](https://github.com/avadhesh18/rssTea) uses GitHub Actions), go P2P/WebTorrent ([HackerNoon single-file app](https://hackernoon.com/how-i-built-a-complete-p2p-rss-podcast-app-in-a-single-html-file-uo1631z1)), or fall back to public CORS proxies ([Wilburn's podcast client](https://thomaswilburn.github.io/wc-book/cs-radio.html)).

**The donor comms layer** (`/mnt/tera/working/programming/OpenHearth/ohPrimer/rebuild/src/scripts/40-comms.js`) is a complete, battle-designed version of that last strategy: SSRF guard (`assertSafeFetchUrl`) before every fetch; direct-first with a short 5 s timeout ("CORS failures are fast, hangs are not"); an explicit, profile-scoped **consent gate before any public proxy is used** (cors.eu.org → allorigins.win → codetabs.com), with the prompt naming exactly which third parties would see the URL; background feed refresh *never* prompts — proxies only if already consented; size caps (25 MB text, 300 MB audio, enforced mid-stream via reader with progress callbacks); conditional GET with ETag/Last-Modified, plus 304/404/410/429+Retry-After handling; and a documented note that media hosts (pdst.fm, megaphone.fm, transistor.fm) don't send CORS headers so `<audio>` plays but `fetch()` needs the proxy. This is the reference design for "no server, still honest about egress."
